01
How to Use This SOP
Read before building any custom report

Custom reports are one of the most proliferated — and least governed — configuration objects in Workday. Most tenants accumulate hundreds of reports over time, many duplicated, outdated, or accessible to the wrong people. This SOP enforces a build-with-intent approach: every report has a named owner, a defined audience, a security review, and a lifecycle plan from day one.

⚠️ Warning
Custom reports in Workday respect the security of the user running the report — not the report owner. A report built by an HRIS Admin and shared with managers will only show each manager the workers they can see based on their own security group. However, reports shared too broadly can still expose more data than intended. Security review every report before sharing.
✅ Tip
Create one copy of this SOP per report. Naming convention: SOP_RPT_[ReportName]_v1.0_2026.html. For integration-enabled reports, cross-reference the corresponding Vol. 01 (EIB/Studio) SOP.

Report types, data sources, and framework concepts

💡 Rationale
Always start with Advanced report type — even if your current requirements are simple. Advanced reports support calculated fields, complex filters, and integration eligibility. Starting with Simple and needing to rebuild as Advanced later is a common and avoidable rework cycle.
Primary Business Objects

The top-level data source for a report. All Workers, All Active Workers, All Positions, Compensation Proposals, Job Applications. Your BO selection determines which related fields are accessible.

Related Business Objects

Sub-objects accessible via the primary BO. E.g., from All Workers you can traverse to Manager, Compensation, Position, Location. Each traversal adds a join — deep traversals can impact performance.

Calculated Fields

Custom fields computed at runtime — date differences, text concatenations, conditional logic, number formatting, lookups. The primary tool for business-specific metrics not available in standard fields.

Filters vs. Prompts

Filters are hardcoded — the report always applies them. Prompts ask the user to input values at runtime. Use prompts for date-range reports and org-scoped reports used by multiple stakeholders.

Pre-Build Checklist
Complete before creating any new custom report
  • Check if a delivered Workday report meets the need — avoid rebuilding what already existsSearch Workday Community for delivered reports before building custom. Copy and modify delivered reports rather than building from scratch where possible.
  • Check the tenant for existing custom reports that overlap with the requestRun a report inventory search before creating a duplicate
  • Report requirements documented: business question, required fields, filters, output format, audience
  • Named report owner identified — responsible for accuracy and lifecycle decisions
  • Data sensitivity assessed — does the report include PII, compensation, health, or banking data?If yes, security review required before sharing with any audience beyond HRIS Admin
  • Integration eligibility requirement confirmed — will this report feed an EIB or Studio integration?If yes, use Advanced report type and ensure Integration-Eligible flag is set
04
Custom Report Build — Step-by-Step
Building a custom Advanced report from scratch
1
Create the Report
Search Create Custom Report. Enter the report name per convention (e.g., RPT_Headcount_ByOrg_Active). Select report type: Advanced. Select the Primary Business Object — this is the most important decision in report building. All field traversals stem from this choice.
✅ Tip
Use All Active Workers for headcount and people analytics reports rather than All Workers — it pre-filters to active employees and significantly reduces query scope and runtime. Use All Workers only when terminated workers are intentionally in scope.
2
Add Columns (Fields)
Navigate to the Columns tab. Add fields by traversing the business object hierarchy. Click Add Field and use the field browser to navigate from the primary BO to related BOs. Add: Worker ID, Full Name, Position, Supervisory Org, Manager, Location, Employee Type, Hire Date — then the report-specific fields from your requirements doc.
📋 Note
Column order determines the output column order. Arrange fields logically — identifier fields first (Worker ID, Name), then classifiers (Org, Location, Type), then the specific data fields. This makes downstream data processing significantly easier for report consumers.
3
Configure Filters
Navigate to the Filters tab. Add filter conditions to restrict the data set. Common filters: Active status, specific orgs, country, hire date range, employee type. For each filter, set the operator (equals, in list, greater than, is not empty) and the value. Chain multiple filters with AND logic (default) or OR where business logic requires.
⚠️ Warning
Filters do NOT override security — they narrow the data set further. A user who cannot see a worker due to their security group will never see that worker in a report, regardless of filter configuration. However, missing a filter (e.g., forgetting to filter to Active workers) can produce unexpectedly large data sets that increase runtime and confuse consumers.
4
Add Prompts (Optional)
Navigate to the Prompts tab. Add runtime prompts for fields that should be user-selectable: Effective Date, Organisation, Country, Date Range. Mark prompts as required or optional. For date-range reports used in integrations, prompts are typically removed — filters are hardcoded to relative date logic (e.g., last 24 hours).
5
Configure Output & Grouping
Set the Sort order (typically Supervisory Org → Worker Name). Add Group By if subtotals or grouping headers are required. Navigate to Output and confirm the default output format. For integration reports, set output to XML or CSV as required by the receiving system. Enable Integration-Eligible flag if this report will feed EIBs.
6
Save & Run Initial Test
Save the report. Click Run. Review the output: confirm row count is as expected, all columns are populated, filters are working, and no unexpected data is visible. Compare against a known data set (e.g., org chart headcount) to validate accuracy. Document expected output in Operator Notes.
05
Calculated Fields
Building custom metrics and business logic in Workday reports

Calculated fields extend Workday's standard data with custom computations — tenure in years, compa-ratio percentages, conditional flags, concatenated identifiers, and more. They are one of the most powerful and most under-used tools in Workday reporting.

Calculated Field Function Reference
Function CategoryKey FunctionsCommon Use Cases
Date & TimeDate Difference, Date Add, Date Extract, TodayTenure (years/months), days since last promotion, days to contract end
Text / StringConcatenate, Upper/Lower, Substring, Text LookupFull name formatting, composite IDs, country code mapping
NumericAdd, Subtract, Multiply, Divide, Round, Absolute ValueCompa-ratio, range penetration, budget variance, headcount delta
ConditionalIf/Then/Else, Is Null, Is Empty, SwitchRed/Amber/Green flags, absence tier classification, risk scoring
LookupLookup, Related ValueMapping internal codes to external labels, currency conversion flags
AggregationCount, Sum, Average, Maximum, MinimumTeam headcount, average salary by org, max tenure in department
1
Create a Calculated Field
Within the report, navigate to Calculated Fields tab → Add. Name the field descriptively (e.g., CF_Tenure_Years). Select the function category and function. Configure the inputs — typically field references from the report's BO or static values.
✅ Tip
Prefix all calculated field names with CF_. This makes them instantly identifiable in the field list and distinguishes them from standard Workday fields when reviewing or troubleshooting a report.
2
Build Common Calculated Fields
The following are the most frequently needed calculated fields in Workday reporting:
CF_Tenure_Years
Function: Date Difference (Years)
Input 1: Hire Date (Worker)
Input 2: Today's Date

CF_CompaRatio
Function: Divide
Input 1: Annual Base Salary
Input 2: Grade Midpoint → Round to 2 decimal places

CF_RangePenetration
Function: Divide → Subtract → Divide
Formula: (Salary - Min) / (Max - Min) × 100

CF_ActiveFlag
Function: If/Then/Else
If: Employment Status = Active → "Active" Else → "Inactive"

CF_FullName_LastFirst
Function: Concatenate
Value: Last Name + ", " + First Name
3
Test Calculated Field Output
Run the report with the calculated field added. Spot-check at least 10 records manually — verify the computed value against the source fields. For numeric fields, cross-reference against a known calculation in Excel. For date fields, validate against worker hire dates visible in the worker record. Document expected values in Operator Notes.
⚠️ Warning
Calculated fields return null silently when an input field is empty. A tenure calculation on a worker with no hire date will return blank — not an error. Always test with workers who have missing data to understand null handling before the report goes to stakeholders.
06
Report Security & Sharing
Controlling who can see and run each report
1
Set Report Sharing
Navigate to the report → Share. Add the security groups or users who should have access to run the report. Options: Run (execute only), View (see definition), Modify (edit the report). For most stakeholder reports, grant Run access only — restrict Modify to HRIS Admin and the report owner.
🔴 Critical
Granting Modify access to a report shared broadly allows anyone with that permission to alter the report definition, add fields, or remove filters — potentially exposing data beyond the intended scope. Treat Modify access like admin access.
2
Secure Sensitive Reports via Domain Policy
For reports containing sensitive data (compensation, banking, health), ensure the report is secured not just by sharing, but by the underlying domain security policy. A user without access to the Compensation domain will see blank compensation fields even if they can run the report. Confirm domain security is correctly configured (see Vol. 02) before distributing sensitive reports.
3
Add Report to a Workday Dashboard or Worklet
For reports intended for regular use by specific audiences (e.g., HR Dashboard for HR Partners), add the report as a Report Worklet to the relevant Workday dashboard. Navigate to Maintain Home Page Worklets or the specific dashboard → add the report. This surfaces the report in context rather than requiring users to search for it.
07
Scheduling & Integration Enablement
Automating report delivery and enabling EIB/Studio feeds
1
Schedule Report Delivery
Navigate to the report → Schedule. Set recurrence (daily, weekly, monthly), run time, and time zone. Select output format (Excel, CSV, PDF). Configure delivery: email to recipients, or deposit to a Workday external service / SFTP. Assign the run-as account — use an ISU if the report feeds a system process.
⚠️ Warning
Scheduled reports run as the scheduled user's security context. If the scheduled user's security changes (role removed, group changed), the report may produce incomplete data silently. Review scheduled report run accounts quarterly as part of your integration ISU audit (Vol. 01).
2
Enable for Integration (EIB)
Navigate to the report → Edit → check Web Service Enabled and Enable as Web Service. This makes the report accessible via Workday's REST/SOAP API and usable as the data source for an outbound EIB. Confirm the report output format matches the EIB's transformation expectations (see Vol. 01 Section 03, Step 2).
✅ Tip
Maintain a separate, dedicated report for each integration — never use a report shared with end users as an integration data source. If a user modifies a shared report to meet their needs, the integration breaks silently. Integration-dedicated reports should have HRIS Admin only sharing with Modify locked down.

Managing the report inventory and preventing report sprawl
Quarterly Report Governance Tasks
TaskMethodFrequency
Full report inventory auditRun All Custom Reports system report — export owner, last run date, sharing configQuarterly
Identify stale reports (not run in 180+ days)Filter inventory by last run date → flag for owner review → delete if no longer neededQuarterly
Validate integration-enabled report outputRun integration-eligible reports manually and verify output matches expected schemaQuarterly
Review sensitive report sharingAudit reports containing compensation/PII fields — confirm sharing is limited to intended groupsQuarterly
Review scheduled report run accountsConfirm ISUs used for scheduled reports are still active and correctly permissionedQuarterly
Workday release — check for delivered report updatesReview Workday release notes for changes to business objects and field availabilityPer Release
💡 Rationale
Report sprawl is one of the most common and costly Workday governance failures. Unmanaged report inventories lead to: duplicate data being distributed to stakeholders, stale reports being cited in audits, and integration-feeding reports being modified inadvertently. A quarterly report audit is 2–3 hours of work that prevents months of data quality remediation.
